# リサーチ単位・段階分析パイプライン設計

## 1. 目的

PatentViewerは、独立した共有PDFプールにある同じ特許文献を、リサーチごとに異なる自社技術・調査目的・対象集合で評価する。PDFはファイル数と容量が大きいためリサーチフォルダへ複製しない。PDF原本は共有する一方、比較評価、Embedding、クラスタ、マップ配置、レビューはリサーチ境界の内側に保存する。

10B程度までのローカルLLMには、旧版で実績のある「1回につき1判断または1要約」の小さな仕事だけを要求する。複雑なチャンク読解JSON、構成要件分解、要件対応表は生成させない。各応答へ専用の小さなJSON Schemaを適用し、生成後もPythonで同じ契約を再検証する。

## 2. 変えてはいけない表示契約

脅威マップは5×5マトリクスを維持する。

- 横軸 `similarity`：自社技術との類似度、整数1～5
- 縦軸 `concept_level`：独立請求項の文言上の権利範囲の広さ、整数1（非常に狭い）～5（非常に広い）。内部キー名は既存データとの互換性のため維持する
- 主根拠：独立請求項と自社技術の直接比較
- 補助根拠：技術分野、課題、用語定義、構成関係を理解するための本文箇所
- Embedding：技術／課題クラスタ計算の内部補助。脅威マップの座標そのものにはしない

各座標には類似度理由と権利範囲の広さの理由を残し、説明可能にする。

## 3. データ境界

### 共有してよいもの

`runtime/shared/extractions/<PDF SHA-256>/` に、PDFから機械的に得られる次の情報を保存する。

- `extracted_text.txt`
- `pages.json`
- `extraction_manifest.json`
- PDFハッシュ、抽出日時、抽出器、ページ数、文字数、OCR有無

キャッシュは効率化のための派生成果物であり、原本ではない。`patent_pool/` のPDFを常に正とする。

### リサーチごとに分離するもの

- `research.json`：自社技術、既定の読取方針、5×5評価方針
- `patent_list_{yyyymmddHHMMSS}.csv`：本番環境の優先入力。最新タイムスタンプ1件をCP932で直接読み込む。入力仕様は [PATENT_LIST_CSV_SPEC.md](PATENT_LIST_CSV_SPEC.md) を参照
- `patents.json`：CSVがないデバッグ・手動リサーチのJSON入力
- `pipeline/<patent-id>/`：文献別の段階成果物
- `clustering/<run-id>/`：リサーチ全対象を母集団としたクラスタ計算・命名
- `results/<patent-id>.json`：UI用の確定結果
- `runs/<run-id>/run_manifest.json`：実行条件、段階、成否、成果物参照

対象文献、段階成果物、確定結果、クラスタはすべてリサーチを境界とする。分類は文献の `category` と `tags` で表現する。移行前の `subresearches/*` は読込互換のみとし、新規書込みには使用しない。

新規リサーチはUIから作成し、`research.json`、`company_tech.txt`、初回CSVを検証後に一括確定する。`research.json.lifecycle.status` は `active` または `archived`、`analysis_stale` は最新版CSVへの切替後から全件再分析完了まで真とする。アーカイブではフォルダを移動せず、通常一覧と分析対象から除外して成果物参照を保つ。

法的状態の表示分類は `research.json.legal_status_rules` にリサーチ単位で保存する。CSVの `ステイタス` 原文と完全一致する文字列だけを「権利化」または「審査中」へ分類し、どちらにも一致しない値は「公開」とする。同一文字列を両方へ登録することは禁止する。これは表示・集計用の派生分類であり、変更時に分析成果物を再生成しない。年次の表示・範囲指定にはCSVの `出願日` の年を使用する。

自社技術プロンプトは、当面ユーザーが各リサーチフォルダの `company_tech.txt` へUTF-8テキストとして格納する。分析時は `company_tech.txt` を優先し、存在しない既存リサーチだけ `research.json` の `company_technology` へフォールバックする。将来はアプリ上でアップロードまたは編集し、対象リサーチへの保存、版管理、分析への反映まで画面内で完結させる。

## 4. 原文とキャッシュの選択

リサーチ既定値は `research.json` の `pipeline.source_policy`、文献別上書きは `patents.json` の各文献に `source_policy` を置く。

```json
{
  "pdf": "JPA 2026000001-000000.pdf",
  "source_policy": {
    "extraction": "reextract",
    "reading": "hierarchical_full"
  }
}
```

抽出方針：

- `cache`：PDFハッシュが一致する共有抽出を使用
- `verify_original`：原本ハッシュを検査して共有抽出を使用。不一致・欠落なら再抽出
- `reextract`：原本PDFから強制的に再抽出

読取方針：

- `targeted`：請求項と技術分野・背景・課題・解決手段などの関連章を読む
- `hierarchical_full`：全文を分割して全チャンクを読み、後段で統合する
- `adaptive`：章・請求項の欠落時は全文読解へ昇格し、それ以外は関連章を読む

実際の判断は文献別の `source_decision.json` に確定保存する。PDFハッシュ変更、抽出文字不足、請求項欠落、章欠落、低確信度、人手指定は再抽出または全文読解へ昇格する理由になる。

## 5. 工程と成果物

1. `extract`：Python/pypdfでページ・全文を抽出し、共有キャッシュへ保存する。
2. `structure`：Pythonの規則で章と請求項を分け、独立／従属を仮判定する。`document_structure.json`。
3. `company_profile`：自社技術定義を、特許側と同じ粒度の技術要約と対象課題要約へ1回だけ正規化する。
4. `similarity`：独立請求項を中心とする入力と自社技術をLLMが直接比較し、1～5と短い理由だけを返す。`similarity.json`。
5. `concept_level`：独立請求項の文言上の権利範囲の広さをLLMが1～5と短い理由で返す。複数の独立請求項がある場合は最も広いものを評価する。`concept_level.json`。
6. `summaries`：課題要約と技術要約を別々のLLM要求で作り、Pythonが `summaries.json` に統合する。
7. `embeddings`：各文献と自社基準の技術要約・課題要約を別々にベクトル化する。文献側のベクトル正本はSQLiteのfloat32 BLOB、監査情報は `embedding_manifest.json`、自社側はrun単位の `company_reference.json`。
8. `clustering`：Pythonで技術ベクトルと課題ベクトルを別々にクラスタ計算する。スコープはリサーチ全体。
9. `cluster_names`：各クラスタの要約群だけをLLMに渡し、name 1項目だけを生成する。
10. `semantic_ordering`：正規化したクラスタ重心のコサイン距離から平均連結階層を作り、近いクラスタが隣接する葉順を決定する。左右反転だけは自社に近い端を左／上へ向ける。
11. `finalize`：検証済み成果物とクラスタIDを既存UI互換JSONへ原子的に確定する。

### 高密度なルールベース前処理

LLMの4分析、Embedding、クラスタリング、UI結果の契約は維持し、LLMへ渡す `patent_text` の生成前に決定的な前処理層を置く。

- `structured_document.json`：ページと特許段落の境界を保ち、安定した段落ID、章、役割、原文ハッシュ、完全重複、定型句、繰返しヘッダー／フッターを記録する。
- `claim_structure.json`：独立／従属と依存先に加え、装置・方法等の請求項種別、構成要件ID、入力・処理・制御等の役割、数値・材料・形状・位置・順序・条件の限定を記録する。
- `evidence_pack.json`：類似度、権利範囲の広さ、課題要約、技術要約ごとに、同じ従来文字数上限内で採用する請求項と段落を決定する。章・役割・自社技術との文字n-gram重なりを採点し、完全重複、近似重複、定型句、タスクに無関係な章を除外する。
- `analysis_inputs.json`：実際にLLMへ渡した文字数、SHA-256、請求項・段落の採用数と章別内訳を監査保存する。

`document_structure.json`、`structured_document.json`、`claim_structure.json` はPDFと抽出本文だけで決まるため、`runtime/shared/extractions/<PDF SHA-256>/` に `preprocessing_manifest.json` とともに保存し、リサーチをまたいで再利用する。マニフェストは抽出本文ハッシュと構造化処理版を保持し、どちらかが変わった場合だけ再生成する。既存ツールとの互換性のためリサーチ別パイプラインにも同じ3成果物を配置するが、共有キャッシュを生成元とする。

`evidence_pack.json` は自社技術と読取方針に依存するため共通化せず、リサーチ別パイプラインに保存する。Evidence Packには自社技術ハッシュ、読取方針、共有構造化成果物のハッシュを記録し、依存関係が変化した場合は再生成する。

権利範囲の広さの評価には独立請求項と構成要件索引だけを渡し、課題要約には請求項や解決手段を混ぜない。類似度と技術要約は同じ原文を機械的に共有せず、それぞれの章上限と役割重みでEvidence Packを作る。LLM APIは従来どおり文字列の `patent_text` を受け取るため、後段の小型JSON Schema、再試行、Embedding、クラスタリング、結果確定は変更しない。

文献別の生成LLMは通常、`similarity`、`concept_level`、`problem_summary`、`technology_summary` の4回を維持する。各Schemaへ追加する根拠は平坦なID配列1個に限定する。類似度・権利範囲の広さは構成要件ID、課題要約は段落ID、技術要約は構成要件または段落IDを返す。Pythonはラベルにページや役割が付随した場合もID本体へ正規化し、タスク入力に採用された候補集合との完全一致を検証する。検証結果は `evidence_traceability`、run集計は `evidence_validation` として保存する。

初回の根拠抽出と判断は1回にまとめる。Python検証で不正ID、候補外ID、請求項不一致を検出した場合は、そのタスクだけEvidence Pack内の許可IDを明示して1回自動再生成する。再生成も不一致ならタスクを完了扱いにせず、その文献を失敗扱いにする。各試行は `<task>_grounding.json` に保存する。これにより通常コストを4回のまま保ち、実際に不整合が起きた文献だけ5回以上になる。

LLMへ渡す本文はPythonが用途別に組み立て、各要求を最大12,000文字に制限する。類似度と技術要約は独立請求項、技術分野、解決手段、実施形態を使用し、権利範囲の広さの評価は独立請求項を優先する。課題要約は背景技術、発明の課題、効果を使用する。

PDFが存在しない文献、またはテキスト抽出量が品質基準を下回る画像中心PDFは、リスト行を削除せず分析状態を `skipped` とする。理由はそれぞれ `pdf_not_found`、`image_only_or_insufficient_text` とし、UIの対象文献一覧と件数に残す。現段階ではOCRを自動実行せず、将来OCRを追加する場合も精度・所要時間・使用モデルを監査対象とする。

### 請求項構造の品質ゲート

- 請求項見出しは行頭の `【請求項N】` と括弧付き同等表記だけを認識する。本文中の「請求項1に記載」は見出しとしない。
- 原文に補正前後など複数の請求項集合が含まれる場合は、`1..N` の最長連番ブロックを採用し、除外見出し数を監査情報に残す。
- `document_structure.json` はスキーマ版3とし、`claim_validation.valid`、連番、空本文、従属先番号を検査する。版3では請求項ごとの構成要件と限定も保持する。
- 請求項0件、非連番、空本文、不正な従属先がある文献は `invalid_claim_structure` とし、LLMへ渡さない。

## スコア根拠の請求項トレーサビリティ

- 類似度と権利範囲の広さのLLM出力には、複雑な引用構造ではなく整数の `claim_number` を1つだけ追加する。
- LLMが返した文章を原文引用として保存・表示しない。
- Pythonは、返された番号が実際に採点入力へ渡した独立請求項に存在することを検証する。
- 真偽値、文字列、存在しない番号、対象外の従属請求項、空の原文は不整合として棄却する。
- 検証成功時だけ、Pythonが `document_structure.json` から請求項原文をコピーし、SHA-256とともに `claim_traceability` へ格納する。
- 不整合時は `verified: false` と棄却理由を監査成果物へ残すが、ハルシネーションした番号や原文をUIへ表示しない。
- UIは検証済みの「類似度: 請求項N」「権利範囲の広さ: 請求項N」だけを表示し、クリック時にPythonが結び付けた原文をダイアログ表示する。
- 既存分析結果には根拠情報がないため、再分析されるまでは従来表示のままとする。
- LLM事前診断は、未準備文献がなく、少なくとも1件の有効な構造JSONがある場合に `READY` とする。`skip.json` に理由が記録された文献は全体開始を妨げず、残りの有効文献を処理する。

文献の最大ページ数や最大容量は固定値で切り捨てず、抽出文字数と用途別入力サイズで制御する。LLMのコンテキスト窓は常時最大値に固定せず、プロンプト文字数から `4096 / 8192 / 16384` の最小適合バケットを選ぶ。LLM出力上限は通常分析で384、512、768トークンの順に再試行し、クラスタ名は128、192、256トークンとする。

LLMの各要求・応答は文献別の `attempts/<run-id>/llm_calls/` に監査保存し、再実行時にも過去の失敗監査を削除しない。文献固有の失敗は `analysis_error.json` に最新状態を保存し、その文献を当該runではスキップして次文献へ進む。次回runでは失敗文献を再試行する。PDF欠落、抽出不足、請求項構造異常は `skip.json`、run全体の失敗・スキップ一覧は `run_manifest.json` に保存する。人手確認済み結果は明示的な上書き指定なしに置換しない。

## 6. 情報表現の分離

- 権利評価：独立請求項を中心に、類似度と限定の少なさを別々に評価する
- 技術表現：入力、処理、推定、制御・出力、システム構成を中心に全文の章別読解を統合する
- 課題表現：従来技術の不足と問題発生条件を中心とし、解決手段を混ぜない

明細書本文は請求項を理解する補助であり、実施形態の記載によって請求項の必須構成や権利範囲を勝手に拡張・縮小しない。

## 7. 実行

```powershell
# 計画だけを作り、PDFやLLMには触れない
python tools/run_research_pipeline.py laser_process_landscape --stage plan

# 共有抽出、章・請求項分割、読取判断まで
python tools/run_research_pipeline.py laser_process_landscape --stage prepare

# Ollama段階分析、Embedding、リサーチ全体クラスタ、UI結果確定まで
python tools/run_research_pipeline.py laser_process_landscape --stage execute
```

UIの一括分析ではアプリ専用Ollamaを空きローカルポートで管理する。GPU名ではなく、総VRAM、空きVRAM、予約領域、モデルとKVキャッシュの見積りから生成並列数、Embeddingバッチ数、冷却間隔を決定する。GPUが20GB以上かつCPUメモリが64GB以上の環境では本番向け永続シャードモードを自動選択する。このモードでは500件単位で生成とEmbeddingを完了して文献別成果物を永続化し、モデルと文献構造のメモリ参照を解放する。全シャード完了後に保存済みEmbeddingを再読込し、リサーチ全体を母集団として一度だけクラスタリング・命名する。それ未満の環境では、現行テスト機と同じく全対象の生成をタスク別にまとめ、生成完了後に一度だけEmbeddingモデルへ切り替える。`--cooldown-seconds` の待機は一定文献相当の生成呼出しごとに行う。文献別 `analysis_progress.json` に完了タスクを保存し、停止・障害後は未完了タスクだけを再実行する。文献固有のJSON生成・Schema検証・Embedding検証エラーは `analysis_error.json` に記録し、その文献だけを当該runでスキップする。キャンセル、Ollama接続障害、全体クラスタリング障害は文献スキップへ変換せず、全体を停止する。実行履歴は最新5件とするが、文献別の実行監査はrun IDごとに保持する。500件を超える集合は全ペア距離を作らず、固定射影とMiniBatch cosine K-meansでクラスタリングする。

既存のUI結果を意図して置換する場合だけ `--overwrite` を付ける。通常リサーチ全件の前にDEBUGの少数文献で、類似度と権利範囲の広さの理由が独立請求項と整合すること、5×5の説明可能性、技術／課題要約の混同がないことを人が承認する。

## 8. 可視UI協働

画面上部の `Pipeline` から、リサーチの対象件数、準備・分析・確定件数、既定の抽出／読取方針、preflight状態を確認できる。可視DOMには次の協働targetを公開する。

- `pipeline-open`、`pipeline-refresh`
- `pipeline-prepare`
- `pipeline-execute-confirm`、`pipeline-execute`
- `pipeline-job-pause`、`pipeline-job-resume`、`pipeline-job-cancel`

Codexによる開始は、実行中の可視UIコマンドと同一client・environmentであることをサーバーが検証する。LLM実行はpreflightの全項目成功と可視チェックボックスによる明示確認を必須とする。BridgeのPause、Resume、Cancelはバックエンドジョブのcontrol fileへ伝播し、各文献・各LLM呼出しの境界で協調停止する。長いLLM HTTP呼出しそのものは途中中断せず、応答後の次checkpointで制御を反映する。

## 9. 技術マップの表示閾値

技術マップでは、クラスタ計算・命名・文献へのクラスタ割当を先に全件分保持し、UIの「最小クラスタ件数」で表示だけを切り替える。選択値を `N` とした場合、現在のリサーチおよび検索・年・ステイタス等の絞り込み結果に対して、所属文献が `N` 件未満の技術クラスタと課題クラスタを軸から除外する。クラスタ成果物の再計算や削除は行わず、セルを選択していない文献一覧にも影響させない。

既定値は `1`（すべて表示）、選択肢は `1 / 2 / 3 / 5 / 10` 件以上とする。閾値変更時に技術マップのセル選択が残っている場合は、非表示セルを参照し続けないようセル選択だけを解除する。協働操作では `technology-cluster-min-size` targetへの `select` を公開する。

軸は技術クラスタ、課題クラスタをそれぞれ意味の近い順に固定する。セル背景は文献件数密度だけに使用し、自社技術との相対的近接度は左右エッジ、自社の対象課題との相対的近接度は上下エッジの発光強度として重ねる。これにより、空セルの視認性を損なわず、自社に近いホワイトスペース候補を読めるようにする。脅威マップの5×5評価と表示契約は変更しない。

### 9.1 ホワイトスペース診断

ホワイトスペース分析エンジンと次の計算規則は、将来のUI再設計に備えて保持する。ただし現行UIでは診断カードを表示せず、0件セルは選択不可とする。0件は「現在の母集団・分類・絞り込み条件で未観測」を意味し、市場価値、技術的実現性、FTOの成立を直接意味しないためである。

診断は次の観測可能な代理指標を分離して示す。

- 探索優先度: 同じ課題に対する他技術の文献量、同じ技術の他課題での文献量、上下左右の占有率、自社技術・課題との相対近接度を合成する。
- 実現性の手がかり: 技術と課題が別々の組合せでは成立している度合いを示す。この組合せ自体の実証済み度ではない。
- 自社適合: 技術クラスタと課題クラスタの自社基準に対する相対近接度の平均とする。
- 空白パターン: 意味順に配置したマップ上で上下左右に連続する0件セルを一つの塊として数える。孤立した空白は組合せの見落とし、大きな塊は技術障壁・需要不足・検索漏れ・分類軸不整合を優先仮説とする。

探索優先度は `課題側文献量 30% + 技術側文献量 25% + 自社適合 25% + 隣接占有率 20%`、実現性の手がかりは `技術側文献量 40% + 課題側文献量 30% + 隣接占有率 30%` とする。文献量は表示中の行または列の最大値で正規化し、各スコアは研究内相対値として扱う。`67%以上=高`、`40%以上=中`、それ未満を低とする。

診断UIを再導入する場合は、同じ課題・同じ技術・隣接セルの件数と、追加確認事項（代表特許、類義語・別分類、非特許文献・製品実証、顧客価値、コスト、安全・規制、FTO）を含める。

### 9.2 セル分析グラフ

脅威マップまたは技術マップの件数が1件以上のセルを選択した場合、マップと文献一覧の間に横幅全体のセル分析パネルを表示する。パネルは両マップで共通とし、脅威マップでは `similarity × concept_level`、技術マップでは `tech_cluster_id × problem_cluster_id` をセル識別子とする。選択中の条件で0件になった場合はパネルを表示しない。

年次グラフは、検索語・現在の法的状態・企業条件を反映する一方、年フィルターではデータを切り捨てない。選択中の年範囲に1件以上ある場合は全収録期間を表示し、その年範囲を背景で強調する。

各年にはセル件数、同じ条件の分析済み母集団件数、構成比、現在の法的状態別件数を保持し、棒を「権利化・審査中・公開」の積み上げ色で表示する。パネルには累計件数、ピーク年、直近3年件数、傾向を表示する。傾向ラベルは共通の `unobserved / undated / sparse / emerging / growing / stable / declining` を、技術マップでは「未観測・年不明・散発・新興・成長・安定・減速」、脅威マップでは「未観測・年不明・散発・脅威流入・脅威増加・安定・脅威減少」として表示する。

同じパネル内で「年次推移」と「出願人構成」を切り替えられる。出願人構成はCSV由来の出願人情報を用い、検索・年・法的状態・企業条件を反映した選択セル内の件数上位10社を横棒で示す。横棒全体の長さは同じ条件の選択セル文献数に対する割合、棒内部は「権利化・審査中・公開」の積み上げ色とする。共同出願文献は各出願人に1件ずつ帰属させるため、企業別割合の合計は100%を超える場合がある。

年は可能な場合は出願日から取得する。出願日がない文献では既存の収録年または公開番号から補完した年を使用し、セル内に補完年が含まれる場合は「年情報基準（補完年を含む）」と明示する。年不明文献は累計件数に含めるが棒グラフから除外し、除外件数を注記する。現在年と前年は公開遅延の影響を受ける期間として表示し、その期間に件数がある傾向判定には「暫定」を付ける。
